## Decisions
Points the packet and the decision of 2026-11-10 did not settle, decided in this milestone.

1. **The browser run's end state** (packet §4.3). `run_pipeline(freeze_corpus=False)` (default `True`, so the CLI and the orchestrator are unchanged) stops after verification: `status: "PENDING_CORPUS_ACCEPT"`, `stages.corpus_snapshot = {status: "NOT_ACCEPTED", reason: "awaiting the hand-off accept"}`, the later stages `SKIPPED` with that reason, journaled `PIPELINE_RUN_PAUSED_FOR_CORPUS_ACCEPT` (the counterpart of `PIPELINE_RUN_PAUSED_FOR_SCREENING`). The job ends `succeeded`. The stage stream ends at `corpus_snapshot`; there is no `screening_prepare` stage event.
2. **"Same artifact id for the same inputs" is pinned on the same records.** The snapshot id is a function of the accepted rows, and each row carries its `retrieved_at`, so two harvests of the same cassette (two CLI runs too) never share an id. The golden test copies the browser run's workspace before the accept, freezes the copy with the CLI run's own accept step (`_accept_run_corpus`) and the original with the hand-off accept: the ids, the outcome status and the counts match, and a CLI run of the same search gives the same counts. Making the id independent of `retrieved_at` would change snapshot identity (RELEASE, Packet B) and is not done.
3. **The hand-off accept reads the run's failed databases back from `legs.json`** (`accept_discovery_corpus` in `pipeline/coordinator.py`): the newest run with `corpus_published` (or `raw_published` before M3b-api) gives the same provider warnings the pipeline passes, so a run with a failed database is still accepted `PARTIAL`. It journals `CORPUS_SNAPSHOT_ACCEPTED` (agent `scholar-harness-console`) with the same parameters as the pipeline's row plus `run`.
4. **E1 names** (packet §4.1). Each live provider has `translate(query) -> (executed_query, request, notes)`, the first step of its own `search` (`_record_translation` records the three on the leg), so the preview and the leg cannot drift; `request` is the full mapping and the plan shows it through `public_request`. `compile_plan(protocol, providers=None)` is in `scholar_search/plan.py` and translates the query each leg receives (`leg_query`: the protocol cap bounded by the engine ceiling, as `SearchEngine.run`). bioRxiv has no `translate` (it is off by default and filters locally); a selected provider without one would say `status: "selected"` with the reason in `notes`.
5. **`cannot_express`** (packet §4.1) lists only what the engine really drops: the protocol language (no provider sends a language filter) and, for arXiv, the year window (filtered after retrieval). The packet's other examples are already the translator's `notes` (arXiv compaction) or do not apply (Semantic Scholar bulk search does take `+ | -`).
6. **`GET /screening/corpus` says `STAGED`** for a discovery `verified.json` that waits for the accept (`from_discovery: true`), as it does for staged exports; `EMPTY` stays for a workspace with neither.
7. **What each import rejection means** (packet §4.4). `IMPORT_BAD_TAG`: a non-blank line that is neither a tag nor the continuation of a value (text before the first record, a wrapped line after an author tag); the line is dropped, as before, but now listed. `IMPORT_NO_TITLE`: a record without `TI`/`T1` (RIS) or `TI` (`.nbib`) is **not imported** (before, it was imported as "Unknown Title", and the exact-title tier then merged every such record into one study); `line` is the record's first line (its `PMID` line in `.nbib`). `IMPORT_BAD_YEAR`: a `PY`/`Y1` or `DP` without a four-digit year; the record is imported without a year, as before. Line numbers are 1-based physical lines of the stored file. A `.nbib` block without a `PMID` is still skipped without a rejection, so a RIS file read as MEDLINE gives `SOURCE_NOT_RIS`, not one rejection per line. The importers keep their generator API and expose `rejected` after `parse` is drained.
8. **`limits` is stored verbatim** (a blank string is `null`), at most 2,000 characters, on the staged row, in `CORPUS_SOURCE_STAGED` (`parameters.limits`, with `metrics.rejected`), in `GET /screening/corpus` `sources[]` and in the report's `imports[]`. The three codes are row fields, registered in `console/refusals.py` (`IMPORT_REJECTION_CODES`) and the contract §7 table, never HTTP statuses. The provenance manifest written at accept is unchanged. `tests/cli/test_accept_corpus.py::test_preview_matches_what_acceptance_builds` pins the preview row's exact keys, so it gains `limits: None, rejected: []`.
9. **What a tier count counts** (packet §4.5). A cluster can grow by more than one tier (a second member by DOI, a third by fuzzy title), so the deduplicator records the tier of every merge (`DocumentCluster.merges`, in member order; `DocumentCluster.tier` is the first one, `None` for a singleton). `clusters.json` gives each cluster its `tier` and each member its `merged_by`; `tiers` in `GET /discovery/dedup` and `dedup.by_tier` in the report count **records removed per tier**, so `identifier + exact_title + fuzzy_title == removed`. Recording the tier changes no comparison, order, representative or id: `stable_order`, the SCI ids and the REC→STU map are pinned by digest on the golden cassette.
10. **`clusters.json` shape**: `{schema: "nexus.dedup-clusters.v1", run, method: {title_similarity, year_tolerance, first_author, source: "protocol" | "default"}, clusters: [{cluster_id, tier, representative, members}]}`; a record is `{workspace_id, provider, provider_id, doi, title, year}` (members add `merged_by`). `run` is the newest `search_runs/run_NNN` (the stage follows the run it deduplicates; `run_deduplication`'s signature is unchanged, since the coordinator tests' doubles pin it). `source` maps the method's `defaults` to the packet's `default`. The two `tests/unit/test_deduplication_stage.py` pins "the stage writes only `deduped.json`" now list `dedup/clusters.json` too. The writer reads the deduplicator's parameters with `getattr`, so a test double without them still runs.
11. **`GET /discovery/dedup`** answers from the newest `clusters.json`; `removed_rate` is rounded to 4 places; `near_twins` stays `null` (E4b). The report fills `by_tier` only when `clusters.json` names the report's run and `deduped.json` belongs to it (M3b-api decision 5), else `null`. `DEDUP_NOT_RUN` (404) is registered in `console/refusals.py` and the contract §7 table. GET routes need no allowlist change (GET on any plain `/api/v1` path is allowed).
12. **No import after a browser run, for now** (researcher, 2026-11-10, asked in this milestone: "Keep the rule for now, combine later"). `VERIFIED_EXISTS` still refuses staging a database export once a search run wrote `verified.json`: an export is staged only before any run, a second browser run is allowed before the accept, and nothing is staged or run after it (`CORPUS_ALREADY_ACCEPTED`). So the decision of 2026-11-10's "another harvest or an import is allowed" holds as "another harvest, or an import before any harvest". `GET /screening/corpus` (and so `GET /discovery/handoff`'s `corpus`) gains `staging_refused: {code, message} | null`, the refusal staging would answer now, with a message that names the rule, so the Import and hand-off screens can say why. Test: `tests/console/test_discovery_api.py::test_after_a_browser_run_the_corpus_says_why_an_export_cannot_be_staged` (failed first: no field).
