## Scope notes (from the specs)
- **Phone QR pairing is M2.** Spec 09 puts `/lan/session/*` and `/lan/pair` in
  M2; desktop approval in M1b-1 uses the terminal-only approval code (M1a
  `pairing/begin`, then `redeem`, then `publish`). The plan row's "publish with
  QR pairing" is corrected to match.
- **Accepting the corpus from the UI.** There is no `POST /corpus/accept`
  route (M0 shipped the CLI). The Prepare screen's snapshot-missing state
  shows the `nexus-scholar accept-corpus` command instead of a button; the
  route is deferred.
- **Routes:** the new screens live at `/screening/home`, `/screening/triage`, `/screening/publish` and `/screening/prepare`, beside the legacy `/screening` page (its demo record and its live batch view are pinned by existing suites). The legacy page is retired at M5-slim.
- **Prefetch:** records may be prefetched (spec 03, "next 5 records");
  proposals never are, because reading one records a reveal (M1b-0 review P3-2).

## Deferred
- **The rule-table line** ("From your answers: Include", spec 03/05): the engine has no route that returns the rule-table outcome for a person's answers, and the UI must not compute it. Shown once a route exists (contract change, M1b-2 or later).
- **The shell's "Demonstration data" marker** still shows on live screens; triage carries its own live stamp, as corpus and lineage do. Retiring the global marker is an M5-slim "honest labels" item (plan §8).
- `POST /corpus/accept` (spec 02 accept button): the CLI step is shown instead.
- Phone QR pairing and `/lan/*`: M2 (spec 09).
- **To M2, a torn event or reveal line** (M1b-0 review P3-3; researcher, 2026-11-05): an unreadable line in `events/*.jsonl` or `reveals.jsonl` still fails intake with a 500. It is handled with the phone's offline queue, which adds the next writer.
- **Offline hold** (spec 03 "Offline", `ENGINE_UNREACHABLE`: "your last n decisions are held in this tab"): a decision whose POST fails is not queued; the screen shows the refusal and nothing was stored. The IndexedDB queue with replay is M2 (plan §6 M2 row).
- **Code-field confirm dialog** (spec 09 "Enter in the code field opens a confirm dialog"): Approve is an explicit button; the dialog is cosmetic and moves to M2 with the phone's read-only approve view.
- **Reviewer follow-ups, not fixed here:** the redeem rollback list (`screening.py`) omits the idempotency record, so a failed journal write followed by a retry replays success without a journal row (to M2, with the torn-line refusal); the engine accepts a desktop event with `criteria: []` although contract §3.1 requires them on desktop (to M1b-2, with the contract's next revision).
