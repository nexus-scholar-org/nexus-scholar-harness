Shared rules (step bar, `?console=`, run selector, job streams, refusals, hard rules): `01-plan.md` "Shared by 01–08". Duplicate counts: `05-dedup.md`.

**Purpose.** Before any record is fetched, say how many records and works the harvest is likely to produce, what that means in screening hours, whether the cap will cut any database short, and offer one recommended action the researcher may apply.

**Why.** On 2026-11-13 a harvest returned 1,074 records (1,050 works after duplicates) for a review planned at 150 to 300 studies, and the researcher learned the size only afterwards, by which time the harvest was done and the corpus was one accept away from being frozen. Nothing the researcher saw before pressing "Start the harvest" said how big it would be.

**Changed from the canvas and from `01-plan` and `03-harvest`.**
- **`01` says the Plan screen has no write and shows no count.** Both stay true except for one deliberate addition: an explicit "Count what the databases hold" button that sends read-only count requests (no record bodies, nothing written to the workspace, nothing journaled). The cut "Dry run card" returns as the **Estimate** card, now backed by a real call.
- **The browser computes nothing.** Every figure (per-database fetch estimate, the range, the hours, the threshold test, the suggested cap) is written by the engine; the browser prints them and sends the researcher's pace as a parameter. This follows the discovery hard rule "the browser computes no count the harness did not write".
- **The cap is still the protocol's, plus the per-run override of `03`.** `01` decided the Plan never shows a run override. The estimate card shows the cap in force (protocol or engine ceiling) and a *recommended* per-run cap; it never fills, sends or stores one. "Apply" exists only on Harvest, where the override field already lives (`03` Data out), and on Plan it is a link that opens Harvest with the number prefilled in the field (see Entry / exit).
- **Recommendation, never action.** The recommended cap or the advice to narrow the query is a card the researcher acts on; Start stays a separate click and nothing starts a harvest (accepted decision 2026-11-14: an assistant never accepts a corpus or acts for the researcher; the same holds for a fixed check).
- **Machine output as a draft.** The estimate is the engine's arithmetic on counts the databases reported, shown in a card styled as a draft (dashed `ink-muted` border, label "Estimate · not a count of what will be fetched"), because it can be wrong in both directions (see "Range" and "What each database can report").

## Entry / exit
- Entry: the estimate card is on Plan (`01`), below Limits, and above the cap field on Harvest (`03`) in the ready state. It is not drawn on Harvest once a run exists or the corpus is accepted (`CORPUS_ALREADY_ACCEPTED`: the card is removed, not disabled).
- Exit: no navigation of its own. "Use {n} on the Harvest screen" (Plan) is a link to `/discovery/harvest?cap={n}`; Harvest reads `cap` after hydration (`useLocationParams` pattern of `01`), puts it in the "Cap for this harvest only" field and does not submit. "Change the protocol through inception" (existing link of `01`) is the narrowing action.
- Gate: none. The estimate never blocks Start. It can only warn.
- **Dependency on M10a.** M10a adds database selection and order to the Plan step. The estimate counts the databases that are **selected at the moment of the count**: it takes the same `providers` list the run will receive (`RunBody.providers`, `discovery.py:750`), or the protocol's selection when there is none. If M10a stores the selection in the protocol, nothing is sent; if it makes it a run parameter, the screen sends it with the count exactly as it will with Start. Order has no effect on the estimate (it affects which records a cap keeps, see "Cap"). If M10a changes what the Plan card layout is, this card moves with it; its content does not change.

## Where totals come from today
Read from the code:
1. **`GET /discovery/plan` returns no total.** The answer (`discovery.py:414-428`) is the protocol fingerprint, the query, the cap, key states, and per database the executed string, request, notes, `cannot_express` and `status`. `compile_plan` only calls `provider.translate()` (`plan.py:59-67`), which sends nothing. The dry run has no number in it, and cannot have one without a request.
2. **A total exists only after a request**, on `SearchLeg.reported_total`, which a provider records from the first page it reads (`base.py:59-66`). That happens in two places today: a **harvest** (`POST /discovery/runs`), too late, and a **recall check** (`POST /discovery/recall`): `check_seeds` runs the protocol query unchanged at the protocol cap (`recall.py:167-171`) and stores every leg, with `reported_total`, in `check_NNN.json`, readable at `GET /discovery/recall` (✓ `discovery.py:889`). A recall check is therefore a way to learn totals before a harvest, but it fetches up to the cap from every database to get them, needs seeds, and its legs describe the protocol fingerprint it was made for.
3. **So before a harvest, totals are available only if a recall check for the current protocol fingerprint exists.** The estimate uses those legs when they exist (`source: "recall_check"`, with the check's date) and says so. Otherwise it needs the count-only call below. **The count-only call does not exist today (✗ M10b).**

A prior harvest in the same workspace also has legs, but it is a harvest that already happened; it is shown on `03` as before and is not an estimate.

## The count-only call (✗ M10b)
`POST /api/v1/discovery/estimate`, body `{providers?: [name], cap?: int, pace_seconds?: int}` (`extra="forbid"`, same validation as `RunBody`). A POST because it sends requests to third parties and spends a key's quota; it is read-only for the workspace and writes nothing. It answers `200` with the shape below. It is synchronous (at most six small requests, one per selected database, in parallel); it is not a job and has no stream.

Engine, per provider (✗ M10b): a new `BaseAPIProvider.count(query) -> int | None`, built from the same `translate(query)` request the plan and the harvest use, so the count is for exactly the executed string the researcher sees on Plan. Each provider overrides it:

| Database | Count request (what each API can report) | Notes |
| :-- | :-- | :-- |
| OpenAlex | The planned request with `per-page=1`; read `meta.count`, the field the harvest already records (`openalex.py:256`). One request. Needs the key (F12: `OPENALEX_KEY_NOT_SET`). Precedent: `ReconEngine.corpus_count` (`recon/engine.py:228`) does this for a bare term; the new call must use the plan's filters and string instead. | Exact for the executed string and filters. |
| Semantic Scholar | The bulk endpoint the provider uses (`semanticscholar.py:43`) answers with a `total` (`:152`). | **Not verified:** I could not confirm from the repository that the bulk endpoint honours a zero or tiny page size; the safe call is the first page with `fields` reduced to the paper id, reading `total`. Whether S2's `total` is exact or approximate is documented by S2, not by this code. With no key the call may be refused (`PROVIDER_REFUSED`, `semanticscholar.py:32`) or rate limited, and the shared keyless pool makes this the likeliest database to fail. |
| Crossref | The planned request with `rows=0`; read `message.total-results` (the field the provider records, `crossref.py:119`). | `rows=0` is Crossref's documented way to get a count with no items; not exercised in this repository. |
| arXiv | The planned request with `max_results=1`; read `opensearch:totalResults` (`arxiv.py:265`). | **An upper bound only.** arXiv has no year filter in its API; the provider filters years after retrieval, so `fetched` can be below the reported total (`arxiv.py:235-239`, the plan's `cannot_express`). The estimate treats arXiv's count as a ceiling. |
| PubMed | The planned `esearch` with `retmax=0`; read `esearchresult.count` (`pubmed.py:279`). | `retmax=0` is E-utilities' documented count-only form; not exercised here. A harvest reads at most 10,000 ids per page (`pubmed.py:16`). |
| bioRxiv | None. The provider never records a total (no `_record_total` in `biorxiv.py`, and the API has no boolean search). | `not_countable`. Off by default; if selected, the estimate says it cannot be counted. |

Every count request goes through the provider's own client, so rate limits and the contact address (`MAILTO_NOT_SET`) apply as for a harvest. A failed count is the database's, not the call's: it is returned in that row with the harvest's own codes (`PROVIDER_RATE_LIMITED`, `PROVIDER_TIMEOUT`, `PROVIDER_UNAVAILABLE`, `PROVIDER_REFUSED`, `provider_error_code`, `scholar_search/engine.py:55-75`). The engine keeps the counts in memory for 10 minutes per (protocol fingerprint, provider list), so changing `cap` or `pace_seconds` re-reads them without new requests (`served_from_cache: true`, `counted_at`).

## The estimate
- **Per database.** `fetch_estimate = min(reported_total, cap)`; `cap_binds = reported_total > cap`. For arXiv `fetch_is_upper_bound` is true. A database with no count has `fetch_estimate: null`.
- **Records.** `records.high` = the sum of `fetch_estimate`; `records.low` = the same sum with arXiv counted as 0 (its year filter can remove records after the fact). If any selected database is `not_countable` or `failed`, `records.high` is `null` (no upper bound is possible) and the card says "at least {low}".
- **Works after duplicates, a range with its assumption.** The harness removes duplicates by identifier, exact title and fuzzy title (`05-dedup.md`). Before a harvest the engine cannot know how much the databases overlap, so it states both ends: **low** = the largest single `fetch_estimate` (as if every record of every smaller database duplicated one in the largest) and **high** = `records.high` (no duplicates). The assumption is printed under the range: "At least as many works as your largest database returns, at most the sum of all of them. Real overlap between databases is somewhere in between." If the workspace already has a deduplication from an earlier run, a reference line shows its `removed_rate` (`GET /discovery/dedup`, ✓): "Your last harvest removed {x} % as duplicates." It is a reference for the researcher, never applied to the range. (For the harvest of 2026-11-13 that figure would have read about 2 %: 24 of 1,074 records.)
- **Screening effort.** `effort.hours` = works × `pace_seconds` / 3600, for the low and the high ends, per reviewer. The pace is an assumption the researcher can edit (a number field "Seconds per record", 5 to 600, default 30; `PACE_INVALID` outside it). It is stated beside the figure: "At {pace} seconds per record, for one reviewer. Two reviewers double it." The default is a stated assumption of this spec, not a number from the repository (Open question 1).
- **The cap in force and whether it binds.** One line per database: "{name}: {reported_total} found, cap {cap}: {all of them will be fetched | the first {cap} will be fetched, {reported_total − cap} will not}" from `cap_binds`. The headline cap line comes from `cap.source`: the protocol's, "no protocol cap: the engine stops each database at 10,000", or a run override once one is typed on Harvest. When `cap_binds` is true the text adds the sentence from `03`: "The database stops at the cap, so its count in the report will be a lower bound." **What a cap keeps is the database's own order, not necessarily the most relevant records:** no provider sets a sort or ranking parameter in this code (a search of the five provider modules finds none), so a cap keeps whatever the database returns first; whether that is relevance order differs by database and is not verified here. M10a's relevance and order work changes this for the Explore sample only (accepted decision 2026-11-14); it does not change what a harvest cap keeps. The card says so next to the recommendation, in one sentence.
- **The warning.** `warn.level` is the engine's: `warning` when `works.low` is above the threshold `SIZE_WARN_WORKS` (default 1,000, ✗ M10b constant, shown on the card), `note` when only `works.high` (or an unknown upper bound) is above it, `none` otherwise. The card prints the threshold and the number it was tested against: "The smallest this could be is {low} works, over the {threshold} this tool warns at." There is no field in the protocol for the size the researcher *planned* (a search of the harness finds none), so the threshold is an absolute number, not "more than three times your plan" (Open question 2).
- **One recommended action** (`recommendation`), shown only when `warn.level` is not `none`:
  - `kind: "cap"` when a per-database cap exists that brings the high end to the threshold and is at least `SUGGESTED_CAP_MIN` (100, ✗ M10b constant): the engine finds the smallest cap `c` such that the sum over databases of `min(reported_total, c)` is at most the threshold and returns it with `expected_works`. Text: "A cap of {cap} per database would keep this harvest to at most {high} records. It cuts {k} databases short, so your recall check matters more." Action: "Use {cap} for this harvest" (Plan: link to Harvest with the number prefilled; Harvest: fills the field). It does not set the protocol cap and does not start anything.
  - `kind: "narrow"` otherwise (the needed cap would be under 100, or a database could not be counted so no cap can be promised): "Narrowing the question will help more than a cap: a cap this low would drop most of what a database holds." Action: the existing "Change the protocol through inception" link. No one-click amendment is promised (`01` question 2).
  - Only one of the two is shown, never both, never pre-applied, with its "why" behind an icon (the arithmetic: totals, caps, threshold).

## Refusals
The estimate answers an HTTP refusal only for the workspace and request, never for a single database. Existing codes keep the copy of `01`/`03`: `PROTOCOL_MISSING` (409), `PROTOCOL_INVALID` (422), `MAILTO_NOT_SET` (409; the exact `SCHOLAR_MAILTO=<your email>` line and "Check again"), `OPENALEX_KEY_NOT_SET` (409; refused before any request when OpenAlex is selected without a key, as Start does), `PROVIDER_UNKNOWN` (422, only if `providers` is sent), `CAP_INVALID` (422, a what-if `cap` outside 1 to 10,000), `DISCOVERY_JOB_ACTIVE` (409; counts are not sent while a harvest or a check runs, to leave the rate limits to it), `CORPUS_ALREADY_ACCEPTED` (409), `TOKEN_SCOPE_REFUSED` (403), guard codes, `ENGINE_UNREACHABLE`. New:

| Code (HTTP) | Role | en title | en body | en affects | en action |
| :-- | :-- | :-- | :-- | :-- | :-- |
| `PACE_INVALID` (422) | blocked | Use a whole number of seconds between 5 and 600 | The pace is only used to turn a number of records into hours. | The screening time shown | Edit the pace |

A database that cannot be counted is not an HTTP error; its row shows "failed" with the harvest's own code in words (`PROVIDER_RATE_LIMITED` "the database limited the request rate", and the three others, `03` `leg.code.*`) and the `error` text under Details.

## States
Roles: `include` for no warning, `unclear` for a note, a database not counted or a database that the cap cuts short, `blocked` only for a refusal, `exclude` (grey) for not selected or off by default. Status is always a text badge.

- **Default** (counted, `warn.level` none): eyebrow of the host screen; card "Estimate · not a count of what will be fetched" (draft styling). Rows, one per selected database: name, "{reported_total} found", "will fetch {fetch_estimate}" (arXiv: "up to {n}"), a text badge "All of them" (`include`) or "Cut by the cap" (`unclear`). Under them: "Records: about {high}" ("at least {low}" when the upper end is unknown); "Works after duplicates: {low} to {high}" with the assumption sentence; "Screening: {h_low} to {h_high} hours at {pace} seconds per record, one reviewer"; the cap line; the counted time ("Counted {counted_at}" and "from cache" when served so). No recommendation.
- **Empty** (not counted yet): the card shows one sentence "Nothing has been counted yet. The databases will be asked how many records match your question; no records are fetched." and the secondary button "Count what the databases hold". If a recall check exists for this protocol fingerprint, the card is instead shown from it, with "From your recall check of {date}. Count again to refresh." (`source: from_recall_check`). If the protocol selects no database (`01` Empty), the card is not drawn.
- **Loading** (`aria-busy`): the button reads "Counting" and is disabled; one skeleton row per selected database; the card keeps any earlier numbers greyed with "As of {counted_at}" until the answer arrives. No number from a previous count is shown as current.
- **Error** (typed refusal, `StateCard`): the codes above; `MAILTO_NOT_SET` and `OPENALEX_KEY_NOT_SET` leave the rest of the page working and show the exact line to set. After a refusal the previous estimate, if any, stays with its time.
- **Partial** (some databases `failed` or `not_countable`): the rows that were counted show as above; each uncounted row says "Not counted: {reason}" in the `unclear` role with its code in words; `records.high` and `works.high` are `null`, so the card reads "At least {low} records; the upper end is unknown because {names} could not be counted" and `warn.level` is computed from the lower end only (`warning` if `works.low` is over the threshold, otherwise `note`: "The size cannot be bounded"). `recommendation.kind` is `narrow`. A second "Count again" is offered; it re-asks only the failed databases when the others are cached.
- **Offline** (engine unreachable): the last estimate stays with "As of {time}"; "Count what the databases hold" is disabled with "needs the engine on this computer". Nothing is queued.
- **Protocol changed.** If the estimate's `protocol_fingerprint` differs from the plan's current one (the protocol changed, or an amendment landed, after the count), the card says "The protocol changed since this was counted" and shows no figure until counted again. On Harvest, the same rule: a stale estimate never sits above the Start button as current. A changed provider selection (M10a) changes the provider list and invalidates the cached counts the same way.
- **After a run exists or the corpus is accepted:** the card is removed (not disabled); the run's own legs are the record.
- **Warning present** (`warn.level` `warning` or `note`): above the rows, a banner in the `unclear` role: `warning` "This harvest is likely to be large: at least {low} works, over {threshold}."; `note` "This harvest could be large: up to {high} works, over {threshold}." Then the single recommendation card (cap or narrow) with its "why". The banner states a fact about the estimate; it does not say the question is wrong.

## Keyboard
Focus order: skip link, shell, step bar, h1, the Limits card, the Estimate card: "Count what the databases hold", the pace field (when numbers are shown), the "why" icon button of each figure, the recommendation's action, then the rest of the page. `Enter` in the pace field re-reads the estimate with the new pace (cached counts, no requests); it never submits Harvest. After the count the result is announced politely ("Counted. {low} to {high} works.") and focus stays on the button; after a refusal focus moves to the card heading. On Harvest the field's focus order is unchanged, and the recommendation's button comes before the cap field. No single-key shortcuts.

## Accessibility
- The card is a labelled region; every badge ("All of them", "Cut by the cap", "Not counted") carries words, so no state rests on colour. The banner is `role="status"` when it appears after a count and `role="alert"` only for refusals. Figures are text in the data face, never images; the range reads "{low} to {high}" and the unknown end reads "at least {low}", which a screen reader reads whole.
- The "why" icon is a button with the visible label "Why this" and `aria-expanded`; its content is the arithmetic (totals, cap, threshold) in plain text. The pace field has a visible label, `aria-describedby` for its help, `inputmode="numeric"`, and `aria-invalid` on `PACE_INVALID`. "Count what the databases hold" in progress has `aria-busy` and announces "Counting".
- Contrast pairs from tokens; the `unclear` and `include` roles appear as badge text in the role's full colour on its `-soft` tint, never as ink text on a tint; `blocked` is text and icon colour only.
- RTL (ar): the layout mirrors; counts, hours, years, the cap, run ids, the `SCHOLAR_MAILTO=<your email>` line, database error text and fingerprints are `dir="ltr"` with Latin numerals; the sentences are translated and flow right to left, with the numbers inside them isolated (`<bdi>`), so "{low} to {high}" does not reverse; the range separator is the word, not a dash. Database names are product names, not translated.
- Targets at least 44 px.

## Open questions
1. **What default pace for the hours figure?** There is no screening-pace value in the repository. *Recommendation:* 30 seconds per record for title and abstract screening, per reviewer, editable on the card, labelled as an assumption; the number is an engine constant so it can change in one place.
2. **What should the warning threshold be, given no field records the size the researcher planned?** *Recommendation:* an absolute 1,000 works for M10b (about 8 hours at 30 seconds), shown on the card with the number it was tested against; recording an "expected studies" range belongs to inception and the protocol, and would let a later milestone warn at a multiple of it.
3. **Should the count run automatically when Plan opens?** *Recommendation:* no. An explicit "Count what the databases hold" button, because each count spends quota (OpenAlex now needs a key; Semantic Scholar's keyless pool is shared) and a page reload should never do that. If a recall check for the current protocol already holds totals, show them without a request.
4. **Should an estimate be recorded in the workspace and the journal, as the recall check is?** *Recommendation:* not in M10b. The run's legs already record `reported_total` and `cap_hit` for what was actually fetched, and an estimate is advice, not a method step; if the researcher wants the pre-harvest counts in the methods text later, add a `DISCOVERY_ESTIMATE` event then.
