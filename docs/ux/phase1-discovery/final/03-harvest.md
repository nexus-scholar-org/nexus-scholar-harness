**Purpose.** Start the search against the databases the protocol selects, watch each database's progress as it happens, stop it if needed, and read how each database ended, counted against its own reported total.

**Changed from the canvas.** The board shows only the running state; this spec adds the ready state before it and the end states after it. Every cut, with the board element:
- **No per-database stop and no slice yield.** "Stop arXiv", "Stop this slice" and the card "Yield per query slice so far" (with "In the UAV v0.3 review, nine slices returned about 1,600 records and no include") are cut: the engine has no leg cancel and no slice model (packet §4.3 says so). There is **one Cancel for the whole harvest**: "Stop the harvest and keep what was fetched". It keeps the records already fetched, archives the run `PARTIAL` (the job ends `cancelled`, the legs it stopped read `stopped` with the note "cancelled by the researcher") and builds nothing from it (no dedup, no corpus). The board's "with your reason" is cut: the cancel route takes no reason.
- **No "Split by year" and no "Retry later"** buttons. No route splits a leg or retries one. A harvest again (allowed before the accept) repeats every selected database; the screen says so.
- **The headline "3,506 records so far".** It is a sum of legs made in the browser. No route reports a running total, so no total is shown while the harvest runs; the per-database counts from `leg` events are. After the run, `GET /discovery/runs` supplies `fetched_total` and `legs_total`, and the headline uses them ("{fetched_total} records fetched from {legs_total} databases"). The badge "Running · 1 of 4 still fetching" becomes "Running" (the count of unfinished legs would be a browser count).
- **"1 not fetched"** on OpenAlex (1,343 of 1,344) is a difference the browser would compute. The row shows `fetched` and `reported_total` as the engine sent them and no derived badge.
- **Cache wording** ("cache hit · 13:58 UTC", "cache: none"): the leg has no cache field. Cut.
- **`CAP_REACHED`** as a code: it is not a failure and not an error code in the leg (the leg flag is `cap_hit`, packet §4.3). The board's row reads "at least {fetched}" with the role `unclear` and the sentence "The database stopped at the cap, so this count is a lower bound." Never shown as complete.
- **`PROVIDER_RATE_LIMITED · HTTP 429 · quota resets [time] UTC`**: the leg has `error_code` (one of `PROVIDER_RATE_LIMITED`, `PROVIDER_TIMEOUT`, `PROVIDER_UNAVAILABLE`, `PROVIDER_REFUSED`) and `error` (free text); no reset time. The row shows the code in words and the `error` text under Details. A failed leg with no `error_code` (a parse error, a bug) shows "This database failed" and the text.
- **The plan rows for PubMed and bioRxiv** ("not selected in the plan", "off by default: cannot evaluate NOT or Boolean operators") come from the plan answer (`status`, and `notes` for the reason), kept as one-line rows below the legs. The board's claim about NOT is shown only when the engine sends it in `notes`.
- **Per-run cap override**: a field "Cap for this harvest only" exists on the ready state. It is sent as `cap_override` (integer 1 to 10,000) and the run shows `cap_source: "run_override"` on every leg and the run's `cap_override` (decision 7). The plan (01) never shows it.
- **Database subset** (`providers`): the board has no provider choice on Harvest (its only database picker is on the Plan board, which 01 cuts). `providers` is **not sent**; the run uses the protocol's selection, and `PROVIDER_UNKNOWN` cannot occur.
- **Optional `note`** (≤ 2,000 characters): a free-text box "Note for this run (optional)", sent as `note`, shown on the run detail and printed in the report. The board has none; it is the one field the route offers that the board lacks (`POST /discovery/runs` body). It is not a reason for cancelling.
- **"If you stop" card**: kept, reworded to what the engine does (fetched records are kept; the run is archived Partial; nothing is built from it; earlier runs are not changed). The board's "run 2's files stay and are named stale" is cut: `stale` means a later run's records became the corpus (M3b-api decision 3), which a cancelled run does not do.
- **"Each leg is journaled with its executed string, reported total, fetched count, cap flag, cache use and UTC date"**: reworded to "The databases, queries and counts are saved with the run and printed in the search report" (no cache).
- **A finished run never says "corpus ready for screening".** A run that ends `PENDING_CORPUS_ACCEPT` is not frozen (decision 2026-11-10). The end state leads to Duplicates (05), Report (06) and Hand-off (08).
- **"Run from the terminal" disclosure** (`uv run scholar-harness discover run --run 3`) and the phase ladder: cut as in 01.
- **Machine output as a draft.** The legs are the engine's record of what happened, not a proposal; no draft styling. The executed query shown per leg is the engine's text, in a data face.

## Entry / exit
- Entry: the step bar; "Continue to Harvest" on 02; a direct URL; a reload mid-run reattaches through `active_job`.
- Exit: after a run ends: "Go to Duplicates" (brand), links to the run's Report and to the Hand-off, "Harvest again" (secondary). The step bar leaves to any step.
- Gate: the Start button needs no precondition on the screen: the engine refuses (`PROTOCOL_MISSING`, `PROTOCOL_INVALID`, `CAP_INVALID`, `MAILTO_NOT_SET`, `CORPUS_ALREADY_ACCEPTED`, `STAGED_IMPORT_PENDING`, `DISCOVERY_JOB_ACTIVE`) in that order. Once the corpus is accepted, Start and the cap field are removed (not disabled) and the run list stays as a record.

## Data out
- Start: `POST /api/v1/discovery/runs` ✓ M3b-api (`discovery.py:735`), `202 {job}`, body `{cap_override?: int 1..10000, note?: string ≤ 2000}`. The engine runs the pipeline in-process (decision 1), writes `literature/search_runs/run_NNN/` (`legs.json`, `raw.json`, `search_report.md`) and journals the run (`DISCOVERY_SEARCH`, the approval record; the browser run's end is `PIPELINE_RUN_PAUSED_FOR_CORPUS_ACCEPT`). The UI writes nothing itself.
- Cancel: `POST /api/v1/discovery/jobs/{id}/cancel` ✓ (`:887`). Waits up to 30 s and may still answer `state: "running"`; the screen then shows "Stopping" until the stream ends `failed` with `job.state === "cancelled"`. After the discovery stage has ended a cancel does not stop deduplication or verification, so the button is not offered then.
No journal row is written by the browser.

## States
- **Default (ready, no run yet)**: eyebrow "Step 3 of 7 · Harvest"; h1 "Search the databases your protocol selects"; lede "Each database receives the string shown on the plan. Nothing is frozen by a harvest; the corpus is frozen on the hand-off screen." Card **What will be searched**: the selected databases from the plan and the protocol cap and its source; the contact-email state (`mailto_set`, with the `SCHOLAR_MAILTO=<your email>` line and "Check again" when not set, as in 01). Card **This harvest** with the form: **Cap for this harvest only** (optional integer; help "Overrides the protocol's cap of {value} for every database in this run. It is recorded on the run and in the report. Leave empty to use the protocol's cap. Between 1 and {ceiling}.") and **Note for this run** (optional). The brand button "Start the harvest". Under it, in order: "Keep this window's console open until the harvest ends; closing the console stops the harvest and keeps what was fetched as a partial run."; and, only while no run exists and nothing is staged, "Starting a harvest means database exports can no longer be added to this corpus (until combined corpora are built). If you have exports, import them first." with a link to Import (04).
- **Running**: eyebrow gains the run and its start time (UTC, from the job's `started_at`); a badge "Running" (brand role, text). The legs table (one row per database, in the engine's order, fed by `leg` events): Database; a bar of `fetched` against `reported_total` beside the text "{fetched} of {reported_total}" (when `reported_total` is `null` the text is "{fetched} of unknown" and no bar); Status in words; Detail (the `error_code` word, or "at least" for a capped leg). The stage list under it, one line per `stage` event as it arrives. The side card **If you stop** with the one secondary button **Stop the harvest and keep what was fetched** (removed once the `discovery` stage event has arrived; a caption then says "Fetching is finished. The remaining steps end on their own."). The form is gone. No total is shown while the harvest runs; it is simply absent.
- **Empty** (no run in `GET /discovery/runs`, nothing running): this is the Default (ready) state. A run list of zero is not an error and no code is shown.
- **Loading** (skeleton, `aria-busy`): h1 area, three leg rows, the form skeleton. No count shown until the answer arrives. While the stream connects to a known active job the table shows rows as they arrive; a job whose `snapshot` has not arrived shows "Reading the harvest".
- **Finished** (job `succeeded`, run `PENDING_CORPUS_ACCEPT`): h1 "The harvest is finished. The corpus is not frozen yet." Headline sentence "{fetched_total} records fetched from {legs_total} databases" (from `GET /discovery/runs`). Legs table from the run detail. The stage list ends with `corpus_snapshot` read as "The corpus is frozen on the hand-off screen" (its `status` `NOT_ACCEPTED`). The text leads to "Go to Duplicates" (brand), "Open the report", "Go to the hand-off". "Harvest again" (secondary) repeats every database; a line says "A new harvest replaces this run as the candidate corpus; this run is then marked stale." Never "ready for screening".
- **Error** (typed, `StateCard`; codes under Details):
  - Refusals on Start: `PROTOCOL_MISSING` (409) and `PROTOCOL_INVALID` (422): shared; `CAP_INVALID` (422): field error on the cap, "Use a whole number between 1 and {ceiling}." (`aria-invalid`); `MAILTO_NOT_SET` (409): the exact line `SCHOLAR_MAILTO=<your email>`, "Put this line in the console's environment, or in a .env file, then start the console again.", and Retry (re-sends Start); `CORPUS_ALREADY_ACCEPTED` (409): "The corpus is frozen, so no harvest is started from here. Screening decisions depend on it." with "Back to screening", and Start is removed; `STAGED_IMPORT_PENDING` (409): "Database exports are staged for import. Accept or remove them before a search run." with a link to Import (04); `DISCOVERY_JOB_ACTIVE` (409, `details.job`): "A harvest is already running." with "Follow the running job" when `job.kind` is `run`, else a link to Recall; `PROVIDER_UNKNOWN` cannot occur (no `providers` sent).
  - A **failed job** (`failed` event, `job.state === "failed"`, `job.error.code`): `PROVIDERS_FAILED` "Every database failed, so nothing was fetched." (the failed legs listed below with their `error_code`); `PROTOCOL_CHANGED_SINCE_SNAPSHOT` "The protocol changed since this review's snapshot; the harvest could not continue." with the link to 01; `BATCHES_INCOMPLETE` "Screening batches are incomplete, so the harvest stopped." ; a snapshot refusal code such as `STAGED_IMPORT_PENDING` shown as above; `DISCOVERY_FAILED` "The harvest failed for a reason the engine did not classify." with `error.message` under Details. The code is always under Details.
  - A failed leg is **not** an HTTP error: it is a row with the role `blocked` text ("Failed · {error_code in words}") and the `error` text under Details; the run is `PARTIAL`.
  - `DISCOVERY_JOB_NOT_FOUND` (404): the shared sentence. `RUN_NOT_FOUND` (404): the shared sentence.
  - `ENGINE_UNREACHABLE`, `TOKEN_SCOPE_REFUSED`, guard codes: shared.
- **Partial**: a run `PARTIAL`: some legs `ok`, some `failed` (each with its code and text) and/or `stopped`. The headline still names `fetched_total` and `legs_total`; the failed databases are listed under it by name and code, with "Their records are not in this run." and "Harvest again" repeats all databases. A capped leg shows "at least {fetched}" and the sentence above. A cancelled run (`CANCELLED` in the job result, `PARTIAL` in the run list): h1 "You stopped the harvest. What was fetched is kept." and "Nothing was built from it."
- **Offline**: engine unreachable. A drop of the stream follows the shared rule (reconnect once; then the last state with "Connection lost · as of {time}" and Retry, after one `GET /discovery/jobs/{id}`). Start and Stop are disabled while the engine is unreachable; the last run list stays readable with "As of {time}". Nothing is queued.
- **Protocol-changed**: for the selected run, `query_text`, `year_min` or `year_max` from the run detail differing from the plan's `query.text`, `query.year_min`, `query.year_max` shows the banner "This run searched an earlier query or year window than the protocol has now." (equality of engine fields; the browser does not decide what changed). The hand-off will refuse such a run (`PROTOCOL_CHANGED_SINCE_RUN`, 08).
- **Stale / older run** (`stale: true` or any run but the newest): read-only, with the badge and sentence from 01's run selector; Start and Stop are not shown for it; "Harvest again" is on the newest run only.
- **Live-only**: yes.
