**The run selector** (Harvest 03, Report 06, and any place that shows a run). It lists `GET /discovery/runs` (`discovery.py:397`, `{runs[], active_job}`, newest first). The newest run is selected when `?run=` is absent. `?run=run_NNN` selects another and is kept in the address; an unknown id is the engine's `RUN_NOT_FOUND` (404) on the run reads, shown as a sentence with a link to the newest run. **Dedup (05) and Hand-off (08) have no run parameter on the engine**: `GET /discovery/dedup` reads the newest `clusters.json` and `GET /discovery/handoff` the newest corpus-published run (`run` in its answer, possibly `null`). They never filter.

**Job streams (SSE).** Used by Harvest (kind `run`) and Recall (kind `recall`).
1. Start: `POST /discovery/runs` or `POST /discovery/recall` answers `202 {job}` (`discovery.py:735`, `:798`). The screen connects to `GET /discovery/jobs/{job_id}/events` through the console proxy (`STREAM_PATHS`, `route.ts:109-110`) with `EventSource`.
2. The stream is replayed in full from the start on every connect: `snapshot {job}`, then `leg`, `stage`, then `done {job}` (state `succeeded`) or `failed {job}` (state `failed` **or** `cancelled`; read `job.state` to tell). `: keepalive` comments every 15 s are ignored. Because it replays, the screen's state is rebuilt from the events alone (the last `leg` event per provider wins, each `stage` once); nothing else is remembered between connects.
3. On a drop: reconnect once, automatically. After a second drop: keep the last state on screen, mark it "Connection lost · as of {time of the last event}", read `GET /discovery/jobs/{job_id}` once (✓ `:855`) and, if the job is no longer running, show its final state; otherwise offer the single action "Retry", which reconnects (and so replays). It never loops.
4. On load, the active job is found through `GET /discovery/runs` `active_job` (a `job` or `null`): a reload of Harvest or Recall mid-job reattaches by connecting to that job's stream. If `active_job.kind` is not the kind the screen shows, the screen says what is running and links to the screen that owns it; it does not stream it.
5. `DISCOVERY_JOB_NOT_FOUND` (404; jobs are in memory and only the last 10 finished are kept): shown as a sentence, "The console was restarted, so this job is no longer known. If it produced a run, the run is in the run list."; the action is "See the run list" (Harvest) and the code is under Details.
6. One discovery job runs per workspace: starting while another runs is `DISCOVERY_JOB_ACTIVE` (409, `details.job`); the card offers "Follow the running job" for a job of the screen's kind.
7. Closing the console cancels a running harvest (decision 1): the run is archived `PARTIAL` with the records fetched. The job screen says so before Start ("Keep this window's console open until the harvest ends").

**Workspace needs a protocol.** Every discovery read except the Import and Hand-off corpus reads starts from the protocol (`_protocol`, `discovery.py`): `PROTOCOL_MISSING` links to inception; `PROTOCOL_INVALID` says so in words. Dedup answers `DEDUP_NOT_RUN` and Recall `RECALL_NOT_RUN` as empty states, not errors.

**Hard rules for every discovery screen.**
- The browser computes no count the harness did not write: every number comes from a field (`fetched`, `reported_total`, `found`, `removed`, `records`, ...). A total over several databases is shown only if a route sends it (`fetched_total`, `identified`), otherwise it is not shown. A bar's width is a picture of two engine numbers, always beside their text values.
- It makes no domain decision: it does not say which database is suitable, whether a miss matters, or whether a duplicate is real.
- It never records an AI decision as HUMAN. This phase has no AI decision; the only HUMAN event is the researcher's reviewed methods text (`PUT /discovery/report/methods`, `METHODS_TEXT_REVIEWED`, 06). Any machine text (executed strings, the methods draft) is styled as a draft.
- A frozen corpus (accepted) is never re-run from the browser: after the accept, Start, Check, Import and Add controls are removed, not disabled (`CORPUS_ALREADY_ACCEPTED` covers a stale tab).
- A capped database (`cap_hit` true on a leg, `completeness: "lower_bound"` in the report) is always shown as a lower bound: "at least {n}" (`discovery.common.lowerBound`), never as the database's full answer, on every screen that shows its count.
- A run that ends `PENDING_CORPUS_ACCEPT` is not "ready for screening": the text leads to Duplicates, Report and Hand-off.
- **One brand button per screen**, 44 px touch targets, light and dark tokens, RTL for `ar` (Latin numerals, `dir="ltr"` on strings, ids, paths, fingerprints, DOIs and executed queries).

**Phone.** `discovery.common.phone.desktopOnly` ("Discovery is done on your desktop. Open this page there.") with a 44 px link "Go to screening" (`/[locale]/screening`). No form, no reads shown. See each spec's Mobile layout.

## States
- **Default**: eyebrow "Step 1 of 7 · Search plan"; Literata h1 "This is what each database will receive" (`discovery.plan.title`); lede "The question comes from the frozen protocol. Each string is sent exactly as written; the executed forms below are the engine's translation, shown before anything is sent." The "Executed string per database" card, the "Limits" card, and the link "Continue to Recall". The fingerprint in the card header.
- **Empty**: a protocol that selects no database (every `providers[].selected` false): the card shows "The protocol selects no database to search." with the link to change the protocol through inception. Not an error; no code. (The engine's answer for this protocol is not exercised in the route tests; the screen renders the list as sent and adds the sentence when none is selected.)
- **Loading** (skeleton, `aria-busy`): h1 area, three provider rows, the limits card. No string, count or cap is shown until the answer arrives.
- **Error** (typed, `StateCard`): `PROTOCOL_MISSING` (409) and `PROTOCOL_INVALID` (422), standing for the screen (`pageHeading`) with the inception link; `ENGINE_UNREACHABLE`; `TOKEN_SCOPE_REFUSED` (desktop-only card); the guard codes. The plan can answer no other refusal.
- **Partial**: some providers `translated`, some `selected` (no preview, reason in `notes`), some `not_selected` or `off_by_default`. Each row names its own status; a `selected` row shows "No preview for this database" plus its notes, never an invented string. `mailto_set: false` is partial too: the strings still show; the contact-email card carries the line to set and "Check again".
- **Offline**: the engine is local, so offline is "engine unreachable". The last answer stays readable with an "As of {time}" caption; "Check again" retries. Nothing is queued; there is nothing to write.
- **Protocol-changed**: the plan always reflects the protocol file as read now; its `protocol_fingerprint` changes when the protocol does. If a tab shows an older fingerprint than a fresh read (after a "Check again"), the card says "The protocol changed since this page was read" and the new strings replace the old ones. Recall (02) and Harvest (03) compare their own fingerprints against this one.
- **Live-only**: no Demonstration marker.

## Questions closed by the researcher (2026-11-10: each recommended answer taken, "all recommended")
1. **What should `/discovery/` do?** The routes cannot say whether the entry page is a plain redirect or a status page. *Recommendation:* a short status page (the step bar and one line per step with its route-derived mark, plus "Continue at {step}"), because a researcher who reloads or returns after days then sees where the harvest stands without reading each screen. A redirect to Plan would hide a running harvest.
2. **How does a researcher change the protocol from here?** The plan says a different query or database is a protocol amendment through inception, but no route opens an existing workspace's protocol as an editable inception draft (the drafts API creates and replaces drafts; a workspace is written at its step 6). *Recommendation:* show the sentence and a link to the inception drafts screen, and promise no one-click amendment until the replace path is reachable from the browser; record that as a deferred item for the inception side.
