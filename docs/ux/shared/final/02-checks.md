# 02 Checks    Status: DRAFT | Shared pattern (Phase 0 Inception and Phase 1 Discovery) | No route of its own: a panel mounted on inception 01 to 06 (`/[locale]/inception/*?draft=rec_<32 hex>`) and discovery 01 to 07 (`/[locale]/discovery/*`), and the readiness list on inception 06 | Milestone M10b (fixed checks, endpoints, panel, dismissal); M10c adds the agent critic as a second source in the same list

Boards: none. The panel reuses the draft styling of `docs/ux/phase0-inception/final/01-scope.md` "Shared by 01, 04, 05, 06 and 07" (item 5), the `StateCard` and the existing badge; it draws no new component. Contract: `docs/roadmap/milestones/M10b-proposals-checks.md` "Fixed checks (no AI)" (normative; this spec details it and does not change it). The recommended action of a check is a link to a field or a proposal as defined in `docs/ux/shared/final/01-proposals.md` (referenced here, not redefined). Typed models: none yet (new, ✗ M10b). Brand: `docs/ux/brand/BRAND_BOOK.md` (status roles, principle 2 "say what is not known", principle 6 "quiet by default", the icon rule), `docs/ux/brand/tokens.json`.

**Purpose.** Tell the researcher, on each step and before the one write, what the engine can see is wrong or thin with the question, the sample, the query, the harvest and the hand-off, say why in one click, point to the one thing to do about it, and keep a record of every warning they chose to dismiss and why.

**Changed from the canvas.** There is no canvas for this pattern; what it changes in existing specs:
- **One list replaces the engine-stated "Checks" card of inception 06** (`06-review.md` "Checks card keeps only checks the engine can state": all criteria decided, both sides, compiler accepted, target folder). Those four lines become checks of this catalogue (`CRITERIA_UNDECIDED`, `CRITERIA_SIDE_MISSING`, `REVIEW_COMPILER_REFUSED`, `REVIEW_TARGET_*`) so the Review shows one readiness list, not two. 06 is amended in the build, not here.
- **The discovery screens gain a panel.** 02-recall, 05-dedup, 06-report and 08-handoff say a miss, a low duplicate rate or a lower bound "blocks nothing" and print the facts; they keep that rule. The panel adds the engine's reading of those facts (a level, a reason, an action) beside them and never disables a button the spec did not already disable. 01-plan and 03-harvest are amended by M10a and are not edited here; the catalogue still lists their checks (`PLAN_*`, `HARVEST_*`) and their specs adopt the panel after M10a merges.
- **No check is computed in the browser.** The engine returns each check with its numbers, level, text keys and action; the browser renders. This follows `apps/research-ui/AGENTS.md` (no domain decision in frontend code) and the rule already used by 06 (preview always from the saved draft). Thresholds are engine constants (like `POOL_THIN_FLOOR`, `recon/gates.py:23`, and `SATURATION_SCANT`, `recon/engine.py:36`), returned beside each check so the card can print "your question has 19 words; at most 12 is suggested".
- **A blocker exists only where the engine already refuses.** Every `blocker` row names the refusal code (see the catalogue). Everything else is a `warning` or a `note`, and neither disables anything.
- **"Why" is a labelled disclosure, not a bare icon.** The brief asks for the why text behind an icon; the brand book bars an icon with no visible label outside a toolbar and the N9 guard bars literal `aria-label` strings. The control is a small stroke icon plus the visible word "Why", a real `button` with `aria-expanded`.
- **No language model.** Every test below is arithmetic, a set test or a string test on data the engine already holds. The agent critic is M10c; its slot is described but not specified (section "The slot for M10c").

## Entry / exit
- Entry: the panel is mounted on each step screen listed in the catalogue and loads with it; the readiness list is the panel on inception 06 (`/inception/review`). A check's action link, or the proposal card it points to (01-proposals), is the way in to the fix.
- Exit: none. The panel never navigates by itself; an action link goes to the field's screen with the field focused (inception) or to the screen named (discovery); Dismiss and Restore stay on the page.
- Gate: no check is a gate. On Review, "Create the workspace" stays disabled while the preview shows a refusal, exactly as 06 says, and the engine decides at the click; open `blocker` rows are the same refusals shown earlier and by name, not a second gate. Open `warning` and `note` rows never disable Create, Accept or any other button.

## The check object
One shape, for every check and for the later critic. All fields are written by the engine (✗ M10b); the browser derives none.

| Field | Meaning |
| :-- | :-- |
| `check_id` | UPPER_SNAKE, stable across versions, never reused for a different test (catalogue). |
| `subject` | `""`, or the one thing the instance is about (a concept name, a database, a term), so a check can have several instances and each is dismissed on its own. `(check_id, subject)` is the instance key. |
| `step` | The owning step: inception `scope`, `explore`, `direction`, `shape`, `criteria`, `review`; discovery `plan`, `recall`, `harvest`, `dedup`, `report`, `handoff`. One owner; the Review list and the stepper badge aggregate. |
| `level` | `blocker` (the engine already refuses; `refusal` names the code), `warning` (worth a look; never blocks), `note` (for information). |
| `source` | `check` in M10b. M10c adds `agent` (see the slot). The proposal source for the recommended action is `check:<check_id>` (01-proposals). |
| `message_key`, `params` | The one sentence as an i18n key and its named slots. The engine also sends the en sentence as `message`, for logs and the methods record, not for display. |
| `why_key`, `why_params` | The "why" text behind the disclosure. One or two sentences, plain words. |
| `evidence` | The numbers and names the sentence quotes, each with its unit (`{kind: "count"\|"share"\|"words"\|"name"\|"doi"\|"run", …}`), same style as proposal evidence. DOIs link to `https://doi.org/{doi}`. |
| `threshold` | `{name, value, default, unit}` or `null` when the test has none. Constants in M10b; not editable by the researcher (Open question 1). |
| `action` | Exactly one recommended action: `{kind: "field", step, field}` (a link to the field on its screen), `{kind: "proposal", proposal_id}` (a card of 01-proposals, created by the engine with `source: "check:<check_id>"`), `{kind: "step", step}` (a link to another screen), each with `label_key`. |
| `refusal` | The existing refusal code for a `blocker`, else `null`. |
| `dismissible` | `true` for a `warning` or `note` that has no gate of its own; `false` for every `blocker` and for the Review target warnings, which are answered by the confirmations in the gate (06). |
| `status` | `open` or `dismissed`. |
| `dismissal` | `{reason, at}` when dismissed, else `null`. |
| `previously_dismissed` | `{reason, at}` when a dismissal exists but its `evidence_digest` no longer matches, so the check is open again (see Dismissal). |
| `evidence_digest` | sha256 over the canonical JSON of `(check_id, subject, evidence)`. Content-derived, like `crit_` ids (`intent.py:265`) and 01's `proposal_id`; a dismissal belongs to one digest. |

The list response:

| Field | Meaning |
| :-- | :-- |
| `shape` | `checks-v1`. |
| `scope` | `{kind: "draft", id, updated_at}` or `{kind: "workspace", protocol_fingerprint, run}`: what the checks describe, so the page can say "as of the saved draft" and detect a newer one. |
| `computed_at` | ISO time. |
| `sources` | The sources that ran: `["check"]` in M10b. |
| `checks[]` | The check objects for the requested step, or for every step when no step is asked. |
| `waiting[]` | Checks that could not be computed yet: `{check_id, step, needs}` with `needs` one of `pool`, `run`, `recall`, `protocol`. Not an error. |
| `counts` | `{blocker, warning, note, dismissed}` for the returned list. |
| `by_step` | When no step is asked: per step `{blocker, warning, note}` open counts, for the stepper badge (one read for the whole stepper). |
| `ready` | Inception only: `true` when no `blocker` is open. |
| `partial` | `[]`, or the facts that make some checks less sure (e.g. `{kind: "pool_partial", databases: ["crossref"]}`). |

## Endpoints (all ✗ M10b; the engine computes, the browser never does)
Inception, on the draft record:
- `POST /api/v1/inception/drafts/{id}/checks`, body `{step?: "scope"|"explore"|"direction"|"shape"|"criteria"|"review"}`. Reads the **saved** draft, the recon session of that draft (pool, legs, binding) and compiles in memory for `REVIEW_COMPILER_REFUSED`. It writes nothing to the draft's fields. It is a POST, like `POST /preview` (`console/api/inception.py:133`) and `POST /steps/{step}` (`:125`), for one reason: the checks that recommend a change (`CONCEPT_TERM_MISSING`) record the proposal with a content-derived id on the draft record (01-proposals "Where a proposal is kept"), once and idempotently; a GET must not write. See Open question 4. Without `step` it returns every step and `by_step`.
- `POST /api/v1/inception/drafts/{id}/checks/{check_id}/dismiss`, body `{subject, evidence_digest, reason}`.
- `POST /api/v1/inception/drafts/{id}/checks/{check_id}/restore`, body `{subject}`.
Discovery, on the open workspace (`_ws(request)`, as every route in `console/api/discovery.py`):
- `GET /api/v1/discovery/checks?step=plan|recall|harvest|dedup|report|handoff` and optional `run=run_NNN` (default the newest). Pure read: no discovery check records a proposal in M10b (01-proposals defines no workspace field).

An unknown `step` answers the existing `STEP_UNKNOWN` (404, `refusals.py:104`; `details.steps` lists them). ## Dismissal
- **Which.** A `warning` or `note` with `dismissible: true`. Never a `blocker` (it is a refusal; dismissing it would change nothing) and never the Review target warnings (their answer is the confirmation in the gate).
- **How.** "Dismiss" on the row opens an inline form with a required text field "Why are you dismissing this?" (the reason) and one button "Dismiss with this reason". The reason is free text, trimmed, 1 to `MAX_TEXT_CHARS` characters (Open question 3). Nothing is dismissed by Escape, blur or navigation. The row moves to "Dismissed ({n})" with the date and reason and a "Restore" button.
- **Restore.** "Restore" returns the instance to open. Restore is a record too; nothing is deleted.
- **What a dismissal belongs to.** One instance and one `evidence_digest`. If the data later changes so the digest differs (a new pool, a new run, an edited concept), the engine returns the check as open with `previously_dismissed {reason, at}` and the card says "You dismissed this on {date}, but the data changed since." The old dismissal stays in the record. A dismissal sent with a stale digest is refused `CHECK_CHANGED`. This keeps a dismissal from silencing a different problem. (Open question 5.)
- **Where it is recorded.**
  - **Before genesis: the draft record.** A new sibling key `check_dismissals: [...]` next to `grounding`, `emitted` and 01's `proposals` in `<workspaces root>/.drafts/<session id>/draft.json`. It cannot go inside `draft`: `Draft` is `extra="forbid"` (`steps.py:152`) and a save replaces only `record["draft"]` (`drafts.py:91`), so a sibling key survives every PUT, as `grounding` does (`drafts.py:95-110`). One `_write` per dismissal (`drafts.py:57-63`). A dismissal does **not** change `updated_at`: a dismissal is not an edit of the answers, and bumping it would make the next save from another tab refuse `DRAFT_CONFLICT` (`drafts.py:84-88`). It is refused `DRAFT_EMITTED` after genesis, like a draft save. Each entry: `{check_id, subject, evidence_digest, action: "dismissed"|"restored", reason, at}`, append-only inside the list; the current state of an instance is its last entry.
  - **From genesis on: the workspace.** `audit/check_dismissals.jsonl` (new file ✗ M10b, listed in `NEW_WORKSPACE_FILES` and `REPLACEMENT_FILES` so `planned_files` returns it in the preview's `files`, `steps.py:428-430`; that changes a public HTTP response, a lane consideration for the milestone). Genesis writes the draft's entries into it first (one line each, with `carried_from: "draft"`), then every later Discovery dismissal or restore appends one line (`{check_id, subject, evidence_digest, action, reason, at, run?}`). Append-only, never rewritten. Journal events through `append_event` (`workspace/audit.py:144`; the action is a free string, as `METHODS_TEXT_REVIEWED` at `discovery.py:689`): `CHECK_DISMISSED` and `CHECK_RESTORED` for each later change (agent `scholar-harness-console`, `AGENT`, `discovery.py:49`; parameters `check_id`, `subject`, `reason`, `evidence_digest`, `method: "HUMAN"`), and `CHECK_DISMISSALS_RECORDED` once at genesis (counts). The file is the record; the journal is the index, because the journal write at genesis is best-effort (as 01-proposals states). A replacement genesis archives the old file with the old protocol and starts a new one: dismissals do not survive a new protocol. Not verified: whether `emit_workspace` writes its files as one atomic unit (`emit.py`, not read in full); the build must test that a failure after the file is written removes it.
  - The record lets the methods text say which warnings were seen and set aside, and why.

## The panel on each step, and the readiness list on Review
**Panel.** Where a screen has a side column (05 side, 06 side, the discovery screens) the panel is a card there; elsewhere it sits in the main column between the proposals list (01-proposals) and the button row. It is a draft-styled card (surface, 1px dashed `ink-muted`): the card holds the engine's suggestion about the researcher's work, while the numbers inside it are plain facts in `data` style. Order inside the panel:
1. **Header**: "Checks · {blockers} to fix · {warnings} to look at". Drawn only when something is open or dismissed or waiting; on a clean step the panel is not drawn (less on screen). Notes are not in the header counts.
2. **Rows**, blockers first, then warnings, in catalogue order. A row: the level badge (words: "Must fix", "Look at this"), the one sentence, a "Why" disclosure, the one action (a link, or a button that opens the proposal card), and "Dismiss" when `dismissible`.
3. **Notes ({n})**, collapsed by default.
4. **Dismissed ({n})**, collapsed, each with date, reason and Restore.
5. **Waiting**: one quiet line "{n} checks are waiting for {need}" when `waiting[]` is not empty (the need as words: "your first search", "a search run", "a recall check").
A stepper badge on each inception step shows the open `blocker + warning` count as text ("2 to check") from `by_step`, never colour alone; the discovery step bar adds the same.

**Level to role.** `blocker` uses the `blocked` role (text and icon colour only, never a fill behind text); `warning` uses `unclear`; `note` uses `exclude` (quiet grey, BRAND_BOOK principle 6). A badge is the role's full colour on its `-soft` tint, with words.

**Readiness list (Review, `06-review.md`).** The side "Checks" card becomes "Ready to create?" and lists, from the all-steps response, every open check of all six steps, grouped "Must fix", "Look at", "Notes", then "Dismissed". Each row carries a text chip "Step {n}" (the engine's `step`, mapped to the numbers in 06) and its action link, so the researcher can leave and come back. The header sentence is one of: "Not ready: {n} must be fixed first." (any open blocker), "Ready to create. {n} still to look at." (no blocker, warnings open) or "Ready to create. Nothing is open." Open warnings are advice: Create is not disabled by them. The compile preview and `target` card of 06 stay; the four engine lines of the old Checks card are now the rows `CRITERIA_UNDECIDED`, `CRITERIA_SIDE_MISSING`, `REVIEW_COMPILER_REFUSED` and `REVIEW_TARGET_*`, and a passing check is not listed (a passing line is not information the researcher needs; the header says "Ready").
**Hand-off (discovery 07)** has no list of earlier steps' checks; it shows its own panel and one link line "{n} open checks on earlier steps" to the first of them, from `GET /discovery/checks` without a step.

## The slot for M10c
The list is one list of check objects with a `source` field. M10b returns only `source: "check"` and `sources: ["check"]`. M10c's critic adds rows of the same object with `source: "agent"` (plus the detail it needs: model, task and version), appended to `checks[]` by the same endpoints; its rows are grouped by level like any other, are never `blocker` (a blocker is an existing refusal), and are dismissed and restored by the same routes and the same record. The panel renders an unknown `source` with the generic label and the same row layout, so no front-end change is needed to show a second source. The reserved label is `checks.source.agent` ("Assistant", not shown in M10b); how a critic is invoked, what it reads and how it reports are not specified here. Nothing in the catalogue, the endpoints or the dismissal record changes when it arrives.

## States
- **Default**: the panel as above; blockers and warnings listed, notes and dismissed collapsed; the Review list with its header sentence. Nothing is pre-expanded, pre-dismissed or pre-applied; no row has focus on load.
- **Empty**: nothing open, nothing dismissed, nothing waiting: the panel is not drawn on a step screen (no "No checks" card). On Review the list is drawn with "Ready to create. Nothing is open." because that sentence is information. Not an error; no code.
- **Loading** (skeleton): a one-line header skeleton and two row skeletons, `aria-busy`; the screen's fields are usable at once (a check never blocks a field). While a recompute runs after a save the previous rows stay with `aria-busy`, so rows do not jump.
- **Error** (typed refusal, `StateCard`; texts through `inception.refusal.<CODE>.*` / `discovery.states.<CODE>.*`):
  - `CHECK_CHANGED` on Dismiss: the row re-reads and shows the new numbers with the polite line "The data changed, so nothing was dismissed. Read it again." (`checks.err.changed`).
  - `CHECK_NOT_FOUND`: the row is removed after a re-read, "That check is no longer there." `CHECK_NOT_DISMISSIBLE`: cannot be provoked from the browser (no Dismiss on those rows); if seen, a row-level sentence with the code under Details. `CHECK_REASON_REQUIRED`: the field is marked invalid, "Write a short reason." `CHECK_NOT_DISMISSED` on Restore: re-read, no alarm.
  - `STEP_UNKNOWN` (404): "The panel asked for a step the engine does not have." with Reload; should not happen.
  - Draft codes `DRAFT_NOT_FOUND`, `DRAFT_ID_INVALID`, `DRAFT_UNREADABLE` (whole-screen card, owned by the screen), `DRAFT_EMITTED` (Dismiss and Restore disabled, rows read-only, decisions shown), `DRAFT_INVALID` / `DRAFT_TOO_LARGE` (the saved draft cannot be parsed: the panel shows the screen's own refusal and no rows).
  - Discovery: `PROTOCOL_MISSING` (409) and `PROTOCOL_INVALID` (422), the shared card owned by the screen; no row is drawn.
  - A check that fails on an unexpected error is returned as `waiting` with `needs: "protocol"` or omitted with its id in `partial`; one broken check never hides the others (tested).
  - Guard codes and `ENGINE_UNREACHABLE`: the shared cards (08 of inception, 07 of discovery).
- **Partial**: some checks computed, some waiting (no pool yet, no run, no recall check): the computed ones show and the waiting line says what they need. A pool with a failed leg (`partial`) says "Computed on a partial pool: {databases} did not answer." under the header, because `EXPLORE_SAMPLE_ONE_SOURCE` and `CONCEPT_NOT_ANCHORED` are then less sure (principle 2: say what is not known). Some checks dismissed, some open: the common state.
- **Offline**: the engine is local, so offline means unreachable. The last list stays with "As of {time}"; Dismiss, Restore and the proposal buttons are disabled with "needs the engine on this computer"; nothing is queued; action links to other screens still work.
- **Stale / protocol changed**: (a) **Draft**: the checks describe the saved draft (`scope.updated_at`). If the page has unsaved edits the panel says "Checks describe the saved draft. Save this page to update them." and keeps the old rows; after a save it recomputes. A draft changed in another tab is the screen's `DRAFT_CONFLICT`; the panel goes read-only with the screen. (b) **Pool**: a new probe changes the pool fingerprint, so pool-based checks recompute and dismissals of them reopen by digest. (c) **Protocol (discovery)**: `scope.protocol_fingerprint` is the protocol the checks were computed for; if the protocol changed after the run, `HANDOFF_SEARCH_CHANGED` and `HANDOFF_PROTOCOL_CHANGED` say so (their data is the engine's `search_changed` and `protocol_changed`, `discovery.py:741`); checks that read a run name that run in their evidence. An older run (`?run=` of a stale run) shows its own checks read-only, as 06 and 05 already do.

## Accessibility
- The panel is a labelled region; rows are `li` in a `ul` labelled by the header; the sentence is real text. Level is a text badge, never colour alone; `blocked` is text and icon colour only, never a fill behind text; `-soft` tints appear only behind badges with the role's full colour (BRAND_BOOK).
- "Why" is a `button` with visible text and an icon, `aria-expanded` and `aria-controls` pointing at the disclosure; the icon is `aria-hidden`. No icon stands alone (BRAND_BOOK "no icon without a visible label").
- "Dismiss" is described by its row's sentence (`aria-describedby`); the reason field has a visible label and `aria-describedby` for "kept in the record"; an empty submit sets `aria-invalid`. Counts and decisions use `aria-live="polite"`; refusals `role="alert"`. The stepper badge text carries the count as words.
- Contrast pairs from `tokens.json`: `ink` on `surface`; role badge text in the role's full colour on its `-soft` tint. The draft look is the dashed border plus the label, not a fill.
- **RTL (ar)**: the layout mirrors; the action link sits at the inline end; check ids, refusal codes, thresholds' numbers, DOIs, run ids and database names are `dir="ltr"` inside `bdi`, numerals Latin; reasons the researcher wrote and the terms quoted from their own text are `dir="auto"`; the sentence slots take `bdi` so a Latin term does not reorder an Arabic sentence; the "Was/Now"-style pairs are never arrows.
- Targets 44 px on the narrow layout; visible focus ring on every control.

## Open questions
1. **Thresholds (⚑ above).** Defaults I am unsure of: `SCOPE_TOPIC_LONG` more than 12 words; `EXPLORE_SAMPLE_ONE_SOURCE` largest share above 0.7; `DIRECTION_SEEDS_FEW` fewer than 3; `CRITERIA_REASONS_UNIFORM` at least 2 exclusions with 1 distinct code; `PLAN_ESTIMATE_ABOVE_TARGET` and `HARVEST_ABOVE_TARGET` above the protocol's planned maximum (ratio 1.0); `DEDUP_RATE_LOW` below 5% with at least 3 databases and 200 records; `HANDOFF_ABSTRACTS_MISSING` below 80%; `HANDOFF_ONE_DATABASE_DOMINATES` above 80%. Also whether they are engine constants only. *Recommendation:* ship these as engine constants returned in `threshold` (not editable), run them over the golden UAV workspace and the 2026-11-13 evidence before the build freezes them, and revisit per-workspace overrides only if testers ask. One caution: the planned size in a protocol today comes from a playbook preset (`scholar_protocol/presets.py`, ranges from 50 to 200 up to 500 to 2,000) and no inception screen sets it, so "150 to 300" in the 2026-11-13 run did not come from the browser flow; the two size checks need either a Plan field for it (M10a's size estimate) or they compare against a preset the researcher never chose.
2. **Do open warnings ever block Create or Accept?** *Recommendation:* no. Only a `blocker` (an existing refusal) disables anything, and the engine still decides at the click; a warning is advice with a recorded dismissal. Anything stricter makes the checks a gate, which M10b does not decide.
3. **What counts as a dismissal reason?** *Recommendation:* free text, required, trimmed, up to the draft's `MAX_TEXT_CHARS` (2,000), no category list. A fixed list invites the same "OUT_OF_SCOPE for everything" habit this milestone is catching; the free sentence is what the methods text can quote.
4. **Should the inception checks endpoint be a POST that records the proposals it recommends, or a pure GET?** I wrote POST (`POST /drafts/{id}/checks`, like `POST /preview`): only one check (`CONCEPT_TERM_MISSING`) recommends a stored proposal, and 01-proposals says proposals are created by a check run. *Recommendation:* keep POST and record the proposal idempotently (content-derived id); the alternative, a GET plus a separate "materialise" call, adds a round trip for one check. The discovery endpoint stays a GET because it records no proposal.
5. **Does a dismissal reopen when the data changes?** I wrote yes: a dismissal belongs to one `evidence_digest`, so a new pool, run or edited concept reopens the check with "You dismissed this on {date}, but the data changed since", and the old dismissal stays in the record. *Recommendation:* keep reopening; the alternative (dismissed until restored) lets a reason given for one run silence a different problem on the next, and reopening costs one click at most.
